How the VisionForge inspection station is built and how work moves through it: where images come from, how each inspection is judged, how recipe changes are approved, and where machine learning sits. The console runs in the operator's browser; smart and IP cameras connect through a small gateway on the station PC; the dashed parts are the planned production integration from intent.md.

System architecture

The console is one page of scripts: dashboard and camera sources, sign-in and navigation, and the inspection engine. Smart and IP cameras reach it through the camera gateway on the station PC. Models load from the CDN or ship with the site, and all state lives in browser storage.

Inspection cycle

One inspection, from the Inspect button (a PLC trigger in production) to the recorded result. The top row is the normal path; the second row shows what each stage does when something is wrong.

Recipe change and approval

Every change to tools, ROIs or limits is a draft until someone with ApproveRecipe accepts it. The approver of a submitted change must be a different person.

Where machine learning is used

Three tools learn from examples instead of hand-set numbers. Each stores what it learned in the recipe, so it is versioned and approved with everything else.

From prototype to production

What the prototype stands in for, and what replaces it on a real line.

PLC interfaceInspect button → hardware trigger, busy/complete, PASS/FAIL outputs and reject signal.
Native camera SDKsThe camera gateway already covers Cognex, HTTP, RTSP and FTP cameras; GigE / USB3 cameras (HIKROBOT MVS, Basler pylon) need SDK adapters in the gateway.
Database and image storeBrowser storage → shared records and images with configurable retention (PASS 7 d, FAIL 90 d).
Server-side sign-inBrowser-held users and hashes → a real identity service, so permissions and the audit trail can be trusted.
